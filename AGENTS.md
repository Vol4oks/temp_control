# AGENT.md

Конфигурация AI-агента для проекта **temp_control** — Rust-прошивка для ESP32-C6 с OLED-дисплеем и DHT11.

## 🎯 Назначение проекта

Прошивка для ESP32-C6 на Rust (`std`-подход, `esp-idf-svc`), которая:
- Опрашивает датчик температуры и влажности DHT11
- Выводит текущие показания на OLED-дисплей SSD1306 (I2C, 0.96")
- Поднимает HTTP-сервер с веб-интерфейсом и API
- Хранит историю измерений в NVS
- Использует FreeRTOS-задачи (через `std::thread`) и каналы для обмена данными

## 🧠 Используемые скилы

Агент **обязан** вызывать перечисленные ниже скилы в указанных ситуациях. Игнорирование скилов — ошибка.

### 1. `embedded-systems`

**Когда вызывать:**
- При работе с периферией ESP32-C6 (GPIO, I2C, SPI, ADC, таймеры)
- При настройке задач FreeRTOS и синхронизации
- При работе с драйверами датчиков (DHT11) и дисплеев (SSD1306)
- При отладке проблем с таймингами, прерываниями, DMA
- При оптимизации потребления памяти и энергопотребления
- При работе с Wi-Fi, TCP/IP, HTTP-сервером на микроконтроллере
- При любых вопросах про `no_std` vs `std`, `esp-hal` vs `esp-idf-hal`

**Что даёт:**
- Понимание ограничений встраиваемых систем (RAM, Flash, тактовая частота)
- Правильные паттерны работы с периферией и RTOS
- Учёт особенностей RISC-V (ESP32-C6) vs Xtensa (ESP32/S3)

**Пример вызова:**
```
@embedded-systems Как правильно организовать обмен данными между
задачей датчика и задачей веб-сервера на ESP32-C6? Канал std::mpsc
или что-то другое?
```

### 2. `rust-skills`

**Когда вызывать:**
- При написании нового Rust-кода (структуры, трейты, обобщения)
- При работе с `Result`, `Option`, обработкой ошибок (`anyhow`, `thiserror`)
- При выборе между `Rc`, `Arc`, `Mutex`, `RefCell` и другими типами
- При работе с асинхронностью (`async`/`await`, `embassy`, `tokio`)
- При проектировании API модулей и крейтов
- При рефакторинге и оптимизации кода
- При написании тестов и бенчмарков
- При работе с макросами, `cfg`, фичами Cargo

**Что даёт:**
- Идиоматичный Rust (borrow checker, lifetimes, ownership)
- Правильные абстракции без over-engineering
- Знание паттернов из экосистемы `embedded-hal`, `embedded-graphics`

**Пример вызова:**
```
@rust-skills Как правильно разделить I2C-шину между дисплеем SSD1306
и другими устройствами на Rust? Нужен ли Arc<Mutex<>> или можно
обойтись без него?
```

### 3. `rust-engineer` (self-check)

**Когда вызывать:**
- **ВСЕГДА** после написания или существенного изменения Rust-кода
- Перед коммитом изменений
- После исправления багов
- После рефакторинга
- Перед запуском `cargo build` / `cargo run`

**Что даёт:**
- Проверка кода на идиоматичность
- Поиск типичных ошибок (unwrap в production, утечки памяти, race conditions)
- Проверка обработки ошибок
- Проверка безопасности (unsafe-блоки, работа с указателями)
- Проверка соответствия best practices для embedded Rust
- Валидация архитектурных решений

**Правило:** скил `rust-engineer` — это **последний шаг** перед тем, как отдать код пользователю или запустить сборку. Он играет роль код-ревьюера.

**Пример вызова:**
```
@rust-engineer Проверь следующий код на идиоматичность, безопасность
и соответствие best practices для embedded Rust:

[код]

Особое внимание: обработка ошибок I2C, работа с каналом между
потоками, возможные race conditions.
```

## 🔄 Типичный рабочий процесс агента

```
1. Получить задачу от пользователя
   ↓
2. Если задача связана с железом/RTOS → @embedded-systems
   ↓
3. Написать код → @rust-skills (при затруднениях)
   ↓
4. Написать код
   ↓
5. Self-check → @rust-engineer (ОБЯЗАТЕЛЬНО)
   ↓
6. Если проверка не прошла → вернуться к шагу 3
   ↓
7. Отдать код пользователю / запустить сборку
```

## 📋 Правила работы

### Обязательные

1. **Никогда не пропускать `@rust-engineer`** после написания кода.
2. **Не использовать `unwrap()`/`expect()`** в production-коде без крайней необходимости — только в `main()` для критичных инициализаций, где паника допустима.
3. **Все ошибки обрабатывать** через `Result` и `anyhow::Result`.
4. **Не смешивать git и crates.io** версии `esp-idf-*` крейтов.
5. **Проверять версии крейтов** на совместимость перед изменением `Cargo.toml`.
6. **Следовать архитектуре проекта**: потоки (`std::thread`) + каналы (`std::sync::mpsc`) для обмена данными.

### Запрещено

- Писать `unsafe` без обоснования и ревью
- Использовать `panic!`/`unwrap` для обработки ожидаемых ошибок
- Игнорировать предупреждения компилятора
- Оставлять `TODO`/`FIXME` без комментария-объяснения
- Менять версии `esp-idf-*` крейтов без явного запроса пользователя

## 🏗️ Архитектура проекта

### Задачи (потоки)

| Задача | Назначение | Периодичность |
|--------|-----------|---------------|
| `sensor_task` | Опрос DHT11, отправка в канал | 2 сек |
| `display_task` | Обновление OLED | 1 сек |
| `web_server_task` | HTTP-сервер, API, веб-UI | постоянно |
| `logging_task` | Сохранение в NVS | 60 сек |

### Обмен данными

```
sensor_task ──[mpsc::channel]──┬──> display_task
                               ├──> web_server_task
                               └──> logging_task
```

### API endpoints

- `GET /` — веб-интерфейс (HTML)
- `GET /api/temperature` — текущая температура (JSON)
- `GET /api/history` — история измерений (JSON)

## 🎛️ Окружение

- **ОС разработки**: CachyOS (Arch-based)
- **Shell**: fish
- **Toolchain**: `riscv32imac-esp-espidf` (через `espup`)
- **Фреймворк**: ESP-IDF (через `esp-idf-svc`, `std`-подход)
- **Целевой чип**: ESP32-C6
- **Прошивка**: `espflash` (через `cargo espflash`)

### Активация окружения

```fish
source $HOME/export-esp.sh
```
